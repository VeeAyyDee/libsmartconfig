# SmartConfig parity addendum: fast mode, start and discovery

Scope: pinned ESP32-S3 ESP-IDF6.0.3 original libsmartconfig, examined by a specification-only author. This is independently written behavior, not original implementation. Existing safe protocol specifications remain the baseline. This new user-requested revision supersedes the prior DROP-IN-01 restrictions that rejected connected STA and pinned every APSTA session to one channel. Exact original observations, public SDK requirements and recommended robust integration are identified separately.

## Exact original observations: fast mode

esp_smartconfig_fast_mode(bool enable) dispatches synchronously to its local operation through esp_wifi_ipc_internal. Local operation writes a persistent one-byte channel dwell setting: true=>50, false=>100, returnsESP_OK. **Untouched original static initialization is150ms (byte0x96), not100ms**. Thus default startup and explicit fast_mode(false) differ numerically in this pinned archive. It is consumed as milliseconds in a one-shot OS timer arm whenever sc_listen_next_channel selects the next channel. No alternative decoder, packet framing, SSID rule, timeout or scan configuration is changed. It applies to all selected protocols through the common hopper. It persists through stop/start; neither lifecycle routine resets it. Setting an option while active is not rejected by original local routine and affects the next timer arm, not the already-armed deadline.

Public header says default normal mode and call before start; therefore supporting pre-start true/false is the required supported workflow. If the fresh API continues rejecting active-session setters as a concurrency policy, document that as a deliberate restriction rather than vendor-equivalent behavior. `true` must no longer return NOT_SUPPORTED. 150/100/50ms are timer requests, not exact end-to-end radio dwell guarantees.

The original hopper iterates ascending candidate-channel bits1..14, wraps to1, writes current/next channel state, calls esp_wifi_set_channel(channel,NONE), then arms timer(period,repeat=false). Driver retuning failure is logged but does not prevent timer rearm. Hopping stops when the channel timer is deinitialized or a decoder locks; fast mode does not accelerate the decoder's locked phase.

## Exact original observations: start, connected STA and APSTA

Internal public start serializes execution through Wi-Fi IPC. NULL config returns INVALID_ARG(0x102). A get_mode failure, AP-only mode(2), or busy SmartConfig status returns ESP_FAIL(-1). Original mode test specifically rejects AP-only; public supported contract remains STA/APSTA, so NULL mode must not be treated as proven supported.

For a permitted idle start, original always calls esp_wifi_disconnect(), including when already disconnected. A disconnect error is logged but startup continues. It performs an OS50ms delay, records logging flag, clears session flags, disables promiscuous reception, initializes AP-list and protocol state, starts discovery scan, then marks started and returns0. The existing association is intentionally relinquished; the original does not automatically restore/reconnect old credentials when stopping. Application Wi-Fi reconnect handlers can race against this, and must cooperate during provisioning.

There is no special APSTA branch that pins capture to the AP channel, no connected-STA rejection and no softAP client-count precondition inside the observed original start. Discovery and subsequent channel hopping operate in APSTA through the same paths. Do not claim this guarantees uninterrupted AP client service. The public SDK expressly allows SmartConfig in APSTA, but esp_wifi_set_channel documentation restricts calls while APSTA is scanning/connecting or softAP has clients. Preserve this distinction: mode support is required; seamless concurrent AP traffic is not established. Let real driver errors be observable/recoverable, do not pretend successful retuning when the driver refuses it.

## Exact original observations: discovery

Start first stops any prior scan, initializes a44-byte scan configuration to zero with show_hidden=true, then calls an SDK-private promiscuous scan API with completion callback. The private result is a driver BSS linked list, **not** wifi_ap_record_t. A fresh implementation should use public asynchronous scan APIs and translate records into its own bounded metadata; it must not cast public records to the private92-byte metadata node.

At first scan-pass start, original clears channel bitmap and sets current/next channel1. For successful results it accepts records whose primary channel is nonzero and RSSI>-85dBm (thus-84 accepted,-85 excluded). It records BSSID6, SSID32, primary/secondary channel; v2 additionally records RSSI and security/cipher metadata. First pass appends records; later passes deduplicate BSSID against prior records and append new ones. It normally performs at least two discovery passes: initial pass counter1, target2. New BSSIDs increase target, but only pass counters<2 use the target-count condition. An empty AP list keeps rescanning, so do not emit SCAN_DONE for an empty/no-usable-AP discovery result. Scan failure delays50ms and retries discovery. Allocator failures can trigger session restart.

Once nonempty discovery is ready, original adds synthetic broadcast/multicast metadata nodes for protocols other than v2 (these are packet-routing aids, not real scan records), masks channel bitmap to2.4GHz supported channels and counts them. If none remain it rescans. It sets an initial channel, disables promiscuous, configures filter mask0x0c, sets callback, enables promiscuous, configures/starts hopper timer, and **then** posts SC_EVENT_SCAN_DONE(id0, no payload). A fresh implementation need not reproduce synthetic nodes or private allocations if observable decoding and candidate-channel selection agree.

Event order on ordinary success: real discovery complete => SCAN_DONE => channel lock FOUND_CHANNEL => validated complete credentials GOT_SSID_PSWD => application connects/acquires IP => SDK ACK sender emits SEND_ACK_DONE. Keep the existing public SDK wrapper/ACK sender. Do not auto-connect on credentials, fabricate scan completion, or deliver stale scan/decoder events after stop. A timeout/restart returns to discovery and may generate another legitimate SCAN_DONE in the same public start lifetime; per-attempt order must remain valid.

## Exact original stop/restart observations

Stop before first start or after stop returns0. Active stop calls scan_stop then clear_ap_list, logs driver failures but continues. It marks stopped, disarms/deletes protocol retry and channel timers, clears channel-timer-active flag, disables promiscuous reception, releases AP metadata and protocol buffers. SDK public wrapper then stops ACK sender and unregisters its credential handler. Original uses Wi-Fi IPC to serialize local stop; fresh code must provide equivalent exclusion from scan/capture/worker callbacks with its own synchronization.

Timeout restart uses internal stop/start, preserves protocol selection and fast dwell global. The original reconstructs restart config from logging flag and zero key fields; do not silently claim original preserves v2 encryption configuration. Fresh implementation should retain a copied immutable session config (including key) across decoder timeout restart, clearly identifying this as robust behavior rather than exact original internals.

## Required integration constraints (public API and safe compatibility)

Only one SmartConfig session/capture owner at once. A restart or stop must cancel owned asynchronous scanning, release result lists, prevent a late WIFI_EVENT_SCAN_DONE from a prior generation entering the current decoder, and quiesce callbacks before freeing state. Event callbacks may call stop; never join the current worker or deliver events while holding a lock needed by stop. Avoid claiming ownership of another component's scan: establish one scan owner or reject conflicts. Preserve error returns from inability to initialize driver/event/worker resources and roll back owned resources.

No ambient-network activity is required for host tests. Use injected scan records and captured synthetic packets. Real hardware scanning/reconfiguration is a separate explicitly scoped validation, never automatically inferred from the host test contract.
