# Scan-assisted SSID recovery and public scan integration

This addendum supersedes earlier first-slice exclusions of scan-assisted decoding. Scanning supplies only public AP metadata; password, token and phone address must still come from valid provisioning frames. A lookup is candidate resolution, not authentication: CRC8 is only an error check. Do not select an AP solely by strongest RSSI or first result when the available identity checks disagree.

## Exact original observations by protocol

**ESPTouch v1:** Header gives totalT,passwordP,SSID CRC and BSSID CRC. SSID length is T-9-P. Original scans cached APs for SSID length plus CRC8 match and BSSID CRC match; when an exact packet-source BSSID is known, exact6-byte equality is used to prefer/identify it. The HT40 matching path explicitly counts matching length/SSIDCRC/BSSIDCRC entries and only accepts exactly one; the ordinary path has additional exact-BSSID and cross-band heuristics. Cache success supplies SSID and BSSID before all SSID octets arrive over length encoding. The original contains hidden-SSID and cross-band branches; full equivalence of those heuristics has not been established by these bounded observations. Do not generalize them to accepting arbitrary ambiguous8-bit CRC matches.

**AirKiss plaintext:** After valid magic (totalT,SSIDCRC) and prefix(password lengthP with prefix CRC), derive S=T-P-1. The original searches cached SSIDs with matchingS and CRC8 and compares the AP BSSID to the appropriate locked802.11 address for the direction. Only an identity-matched entry enables the scan-assisted completion flag. On success it changes required over-air data length from T to P+1 (password plus token), recomputing block count ceil((P+1)/4) and final block remainder (P+1)%4. Thus the sender may omit SSID bytes entirely; the receiver must not wait forever for blocks covering them. The final data block may be short according to P+1. Keep its normal7-bit block-CRC rule over the bytes actually present and index. Existing whole-T ciphertext/decryption behavior for keyed AirKiss is not established as interchangeable with this plaintext short-payload branch; test separately and preserve explicit-key behavior.

**ESPTouch v2:** Original sequence1/header processing obtains AP metadata by locked BSSID or BSSIDCRC helper and copies a33-byte cached SSID into decoder state. The BSSIDCRC helper requires unique CRC match in its ordinary path and additionally matches locked channel and cipher/security metadata; separate cross-band mode exists. If cache has nonempty SSID, later credential processing skips its ordinary SSID-sequence decode stage; otherwise it decodes the SSID sequences. It still receives/decrypts/checks required password and reserved-data sections. The final result rejects all-zero/absent SSID. This is not permission to treat absent SSID as a valid empty network name. Exactly how every cross-band/security heuristic behaves remains outside the currently verified subset; S3 support can restrict matching to its observed2.4GHz AP, exact BSSID when known, declared length and cipher compatibility.

All three use reflected CRC8 polynomial0x8c, initial0, no final xor, as specified by the existing protocol contracts. SSID metadata is at most32 bytes. A hidden AP whose scan SSID is empty cannot supply omitted bytes; continue decoding or wait/restart rather than inventing a name.

## Fresh implementation compatibility requirements

Maintain a bounded owned copy of AP records for the current discovery generation; keys are BSSID, counted SSID, primary/secondary channel and relevant security metadata. Never retain pointers into SDK scan records once result memory is freed. Derive candidate-channel bitmap from accepted scan records, respecting country/driver channel validity and2.4GHz S3 scope.

Expose cached AP information to the own protocol/capture layers through a small owned-data interface. Evaluate matches only after the decoder has validated metadata needed for that protocol. Prefer exact locked/transmittedBSSID identity; verify advertisedSSID length/CRC where available, BSSIDCRC where available, and channel/security compatibility. If only a checksum identifies candidates, require exactly one fully matching candidate; ambiguity must remain incomplete, without credential event. This explicit uniqueness rule is conservative product behavior for any original heuristics not fully established.

For ESPTouchv1, fill only missingSSID and, when required, BSSID bytes from the validated candidate; do not overwrite a conflicting byte actually received from the sender. Then reapply whole-message XOR, SSIDCRC, BSSIDCRC and existing completion checks before releasing credentials. On-air password/IPv4/metadata are still mandatory. For AirKiss use P+1 required data bytes once identity-matched scan recovery is selected; still require every required block and its CRC, obtain the token from byteP, and validate recoveredSSIDCRC. For v2 retain the validated cachedSSID as an alternate source for the SSID stage while preserving all password/reserved encryption/CRC rules and advertisedSSID-length checks. Full over-air SSID transmission must continue to work in either fast setting.

A candidate cache must not make the decoder accept inconsistent prior metadata, join different packet sources, or complete from a password-only prefix without required checksum/token data. Late/conflicting on-airSSID data must not silently replace a previously validated result. Reset cache references/candidate resolution on timeout/stop/new generation.

## Public SDK scan lifecycle

Use esp_wifi_scan_start(&config,false), with zero-initialized config, channel0, ssidNULL,bssidNULL,show_hidden=true, and SDK default active scan timing. Register WIFI_EVENT_SCAN_DONE before starting. Because the fresh implementation uses the public scanner rather than the original private promiscuous scan API, exact RF timing/private discovery flags are not claimed identical.

The event carries status,number,scan_id; use status==0 for success. event.number is8-bit and is not a substitute for esp_wifi_scan_get_ap_num(uint16_t*). Obtain count, bound allocation/copy to configured capacity, then esp_wifi_scan_get_ap_records(&count,array). This getter releases SDK scan-result list; alternatively drain records individually then clear leftovers, or call esp_wifi_clear_ap_list on failure/cancellation. Do not leak result storage. Empty successful scans are real completed hardware scans but are not yet successful SmartConfig discovery: retry according to discovery policy, with no SCAN_DONE until candidate channels are usable.

Public asynchronous scan completion can race with stop/restart. An event handler must check that this generation owns an outstanding scan and session is still scanning. scan_id is informative, not a replacement for ownership/generation coordination. Stop owned scan before freeing metadata. A stale completion after stop must not enable promiscuous or start hopping. Driver scan failures/resource errors require bounded backoff, cancellation support and honest error reporting; do not busy-loop. Original retries failed scans after50ms and normally gathers at least two nonempty passes. Reproducing that two-pass/deduplicate pattern is appropriate; a bounded no-AP retry backoff is an explicit robustness policy.

Disable capture/channel hopping while scanning. Complete/start consuming scan results before retuning with set_channel. Original connectedSTA startup disconnects before scanning; ensure an application reconnect callback cannot silently fight this. APSTA scanning is allowed by SmartConfig API, but client continuity and channel availability depend on driver constraints stated in01. Do not automatically reconnect previous STA association on stop. The application's normal credential event handler remains responsible for connecting to the newly provisioned AP.

## Required tests and honest validation scope

Use deterministic mocked scans, no ambient-network lookup in tests. Verify150ms untouched startup,100ms after explicit fast_mode(false),50ms after true timer arms, persistence across stop/start, regular phone-frame acceptance in either mode, and no timeouts/packet format mutation. Verify connectedSTA start invokes disconnect before scan; APSTA enters real discovery instead of unsupported/fixed-only shortcut; AP-only remains rejected. Test driver get_mode/disconnect/scan-start/scan-status/allocation failures and start/stop during pending scan.

Discovery tests: two successful passes, BSSID deduplication, RSSI-84 accepted/-85 excluded for exact original-filter mode, empty scan retry, only valid scanned channels hopped, no early SCAN_DONE, SCAN_DONE before FOUND_CHANNEL before GOT_SSID_PSWD, stale completion ignored, timeout starts a fresh discovery attempt, resource cleanup exactly once. Event callbacks that stop must not deadlock.

Recovery tests per protocol: omittedSSID + one valid matching AP succeeds; same transmission without cache remains incomplete; wrong SSIDCRC/length/BSSIDCRC/BSSID/channel remains incomplete; collision/duplicate identity handled without guessing; hiddenSSID is not invented; delayed scan generation cannot complete current decoder; explicit over-airSSID still succeeds. AirKiss exercise password+token length1,4,5 and maximum65 to verify shortened final-block boundaries. Include v2 encrypted password/reserved plus scan-sourcedSSID. Contradictory receivedSSID must not be masked by scan substitution.

Current evidence is original static behavioral extraction plus an executable original fast/hop oracle. Full discovery/omittedSSID callback sequences have not yet been run against the original in an independent composed oracle. Do not state full vendor parity or all-phone interoperability from this addendum alone; record which mock, original and hardware cases actually passed.
